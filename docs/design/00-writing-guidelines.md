# 설계 문서 작성 지침

> 상태: 초안 · 적용 대상: `docs/design/` 아래 모든 설계 문서
> 이 문서는 *무엇을* 쓸지가 아니라 *어떻게* 쓸지를 정한다. 현재 작성된 설계 문서는 `01-overview/`와 `decisions/`에 있다.

## 1. 목적

설계 문서는 코드가 말해 주지 않는 것을 기록한다. 코드는 "무엇이 어떻게 동작하는가"를 보여 주지만,
"왜 그렇게 만들었는가", "무엇을 포기했는가", "이것을 바꾸면 무엇이 깨지는가"는 보여 주지 않는다.

이 프로젝트는 패치 시리즈를 새 커널/syzkaller RC에 계속 포워드포트한다. 패치는 교체될 수 있지만
**설계 의도는 유지되어야 한다.** 충돌이 났을 때 패치 텍스트가 아니라 이 문서의 의도를 보고 다시 만들 수 있어야 한다.

## 2. 모든 설계 문서가 답해야 하는 질문

| # | 질문 | 절 제목 | 필수 |
|---|---|---|---|
| 1 | 어떤 문제를 풀기 위해 도입했는가 | `## 해결하려는 문제` | 필수 |
| 2 | 왜 이렇게 설계했는가 | `## 설계` + `## 설계 근거` | 필수 |
| 3 | 다른 선택지는 무엇이었고 왜 버렸는가 | `## 검토한 대안` | 필수 |
| 4 | 이 설계가 다른 요소·결과에 어떤 영향을 주는가 | `## 영향` | 필수 |
| 5 | 이 요소의 신뢰성이 왜, 어느 수준으로 중요한가 | `## 신뢰성 요구` | 필수 |
| 6 | 구조를 한눈에 볼 수 있는가 | `## 구조` (ASCII 다이어그램) | 필수 |
| 7 | 제대로 동작함을 어떻게 판정하는가 | `## 검증 오라클` | 필수 |
| 8 | 무엇이 깨졌을 때 어떻게 나타나는가 | `## 실패 양상과 진단` | 필수 |
| 9 | 아직 모르거나 포기한 것은 무엇인가 | `## 한계와 미결 사항` | 필수 |
| 10 | 관련 코드·증거·다른 문서는 어디인가 | `## 참조` | 필수 |
| 11 | LLM Agent가 산출물을 만들 때 무엇을 지원하고 어떻게 확장하는가 | `## Agent 사용 지침` (8절) | 요소 문서에 필수 |

해당 없는 절은 삭제하지 말고 `해당 없음: <이유>`라고 적는다. 절이 없는 것과 생각해 봤지만 없는 것은 다르다.

## 3. 문서 골격

```markdown
# <요소 이름>

> 상태: draft | reviewed | stable   ·   최종 확인: YYYY-MM-DD   ·   기준: kernel <ref> / syzkaller <ref>
> 관련 패치: kernel 00NN, syzkaller 00NN   ·   관련 게이트: R#

## 요약
세 문장 이내. 무엇이고, 왜 있고, 깨지면 무엇이 잘못 보이는가.

## 해결하려는 문제
## 구조
## 설계
## 설계 근거
## 검토한 대안
## 영향
## 신뢰성 요구
## 검증 오라클
## 실패 양상과 진단
## 한계와 미결 사항
## 참조
```

## 4. 절별 작성 규칙

### 4.1 해결하려는 문제
- 도입 전에 **실제로 관측된 증상**부터 쓴다. "필요할 것 같아서"는 근거가 아니다.
- 증상 → 원인 → 이것이 방치되면 잘못되는 결론, 순서로 쓴다.
- 예: "요청별 PC가 0개라는 사실을 '실행되지 않음'으로 읽을 수 없었다" 같은 식으로 *오독 위험*을 명시한다.

### 4.2 설계 · 설계 근거
- 설계는 결정을 서술하고, 근거는 각 결정에 붙인다. 결정 하나에 근거 하나가 대응해야 한다.
- 근거에는 제약(커널 스레드 모델, syzkaller ABI, 격리 요구 등)과 측정값(증거 경로)을 쓴다.
- 구현 세부는 코드를 가리키고 복사하지 않는다. 코드가 바뀌면 문서가 거짓이 되기 때문이다.

### 4.3 검토한 대안
- 표로 쓴다: `선택지 | 얻는 것 | 비용·한계 | 채택 여부와 이유`.
- 버린 대안이 나중에 다시 유혹적일 조건(어떤 제약이 풀리면 재검토하는가)을 한 줄 적는다.

### 4.4 영향
- 세 방향으로 나눠 쓴다.
  - **상류**: 이 요소가 의존하는 것이 바뀌면 무엇이 깨지는가.
  - **하류**: 이 요소가 틀리면 어떤 요소·결론이 오염되는가.
  - **운영**: 처리량, 자원, 격리, 재현성에 주는 비용.
- "영향 없음"이라고 쓰려면 근거를 적는다.

### 4.5 신뢰성 요구
이 프로젝트에서 계측·격리·프록시 같은 요소는 **결과를 만드는 것이 아니라 결과를 해석할 근거를 만든다.**
따라서 각 요소의 신뢰성 요구는 "정확해야 한다"가 아니라 아래 항목으로 구체화한다.

| 항목 | 작성 내용 |
|---|---|
| 오류 방향 | 거짓 양성(없는 것을 있다고 함)과 거짓 음성(있는 것을 없다고 함) 중 어느 쪽이 더 위험한가 |
| 실패 방식 | 조용히 실패하는가, 크게 실패하는가(fail-open / fail-closed) |
| 관측 가능성 | 오작동을 스스로 알릴 수 있는가. 알릴 카운터·로그는 무엇인가 |
| 재현성 | 같은 입력에서 같은 결과가 나오는가. 나오지 않으면 변동 원인은 무엇인가 |

**작성 예 (remote KCOV).** 이 요소는 시나리오가 어디까지 도달했는지 알려 주는 *디버깅 근거*다.
코드가 아예 실행되지 않은 것인지, 요청 흐름의 순서가 어긋난 것인지를 가르는 판단이 여기에 달려 있다.
그래서 위험한 오류는 거짓 음성이다. PC가 없다는 사실이 "미실행"으로 읽히면 잘못된 설계 수정으로 이어진다.
계측이 건너뛴 경우(포화, 진행 중 section 폐기, 이미 실행 중인 KCOV)를 "관측 없음"과 구분해서 드러내야 한다.

### 4.6 검증 오라클
- 판정 가능한 조건으로 쓴다: 카운터 이름, 파일, 임계값, 게이트 ID.
- 오라클이 무엇을 **증명하지 않는지**도 적는다. (예: 함수 영역 도달 증거는 같은 요청의 순서 증거가 아니다.)
- 음성 대조(있어야 할 것이 없을 때 실패하는가)가 있으면 함께 적는다.

### 4.7 실패 양상과 진단
- `증상 → 가능한 원인 → 구분하는 관측 → 조치` 표로 쓴다.
- "원인을 모르겠다"도 유효한 항목이다. 근거 없이 원인을 단정하지 않는다.

### 4.8 한계와 미결 사항
- 결정되지 않은 것을 결정된 것처럼 쓰지 않는다. `결정됨 / 미결 / 포기` 중 하나로 표시한다.
- 검증하지 못한 주장에는 `미검증`을 붙인다.

## 5. ASCII 다이어그램 규칙

모든 설계 문서는 **`## 구조`에 최소 한 개의 다이어그램**을 포함한다. 요소 하나를 다루는 문서는 구성도를,
흐름이 있는 요소는 파이프라인/시퀀스도를 추가한다.

| 종류 | 언제 | 무엇을 보여 주는가 |
|---|---|---|
| 구성도 | 요소가 여럿일 때 | 경계(호스트/VM/네임스페이스/프로세스), 소유 관계 |
| 파이프라인 | 단계가 있을 때 | 입력 → 변환 → 출력, 각 단계가 남기는 산출물 |
| 시퀀스 | 순서가 의미를 가질 때 | 시간 순 메시지, 누가 누구를 호출하는가 |
| 상태 전이 | 수명주기가 있을 때 | 상태, 전이 조건, 종료·정리 경로 |

작성 규칙:
1. 코드 블록(```` ```text ````)에 넣는다. 폭은 **80자 이내**.
2. 문자는 `+ - | > < v ^ [ ] ( )` 같은 ASCII만 쓴다. 박스 드로잉 문자는 쓰지 않는다.
3. **경계를 그린다.** 커널/유저, VM/호스트, 네임스페이스 경계는 반드시 박스로 구분한다.
4. **화살표에 이름을 붙인다.** 무엇이 흐르는지(RPC, PC, 제어 메시지, 파일)를 적는다.
5. **신뢰 경계와 관측 지점을 표시한다.** 계측이 붙는 곳은 `(K)`처럼 기호를 정하고 범례를 단다.
6. 그림 아래에 **범례와 읽는 순서**를 두 줄 이내로 쓴다.
7. 그림의 이름·경로는 코드와 같은 철자를 쓴다(`syz_open_nfs_lane_pair`, `/nfs-lane/control/arm.sock`).

예시 (형식 참고용):

```text
  +---------------- guest VM ----------------+
  |  syz-executor proc-N                      |
  |    +----------+        +---------------+  |
  |    | client N |--RPC-->| lane server ns |  |
  |    +----------+        |   knfsd (K)   |  |
  |         |              +-------+-------+  |
  |         | KCOV handle          | PC       |
  |         v                      v          |
  |    [ generation ] <--ticket-- [ remote ]  |
  +--------------------|----------------------+
                       v  coverage/extra
                  syz-manager
  (K)=remote KCOV 계측 지점   화살표=흐르는 데이터 이름
```

## 6. 작성 방식

- **언어**: 한국어. 식별자·경로·명령·카운터 이름은 원문 그대로 쓴다.
- **형식**: Markdown. 표는 비교와 매핑에만 쓰고, 논리 전개는 문장으로 쓴다.
- **코드 참조**: `path:line` 대신 `path` + 심볼 이름으로 쓴다. 줄 번호는 곧 낡는다.
  줄 단위 인용이 필요하면 실제 파일의 경로와 해당 줄을 확인해 적는다.
- **증거 참조**: 수치를 쓰면 출처(증거 디렉터리, 게이트 ID, 커밋)를 옆에 적는다. 출처 없는 수치는 쓰지 않는다.
- **날짜**: 절대 날짜(`2026-09-30`)로 쓴다. "최근", "현재"는 쓰지 않는다.
- **단언 수위**: 측정했으면 "측정됨", 코드로 추론했으면 "코드상", 확인 못 했으면 "미검증"이라고 구분한다.
- **중복 금지**: 다른 문서가 소유한 사실은 링크하고 다시 쓰지 않는다. 각 사실의 소유 문서는 하나다.

## 7. 문서 수명

| 상태 | 의미 |
|---|---|
| `draft` | 작성 중. 사실 확인이 끝나지 않았다. |
| `reviewed` | 코드·증거와 대조했고 사람이 검토했다. |
| `stable` | 패치 갱신 시에도 유효함을 확인했다. |
| `superseded` | 대체 문서 링크를 남기고 보존한다. 삭제하지 않는다. |

패치 시리즈가 바뀌면 그 패치를 `관련 패치`로 적은 문서를 재검토한다.
설계 문서의 검증 절차가 현재 코드·부트스트랩 결과와 충돌하면 실제 동작을 확인하고 문서를 고친다.

## 8. LLM Agent가 읽는 문서로서의 규칙

이 문서들은 LLM Agent가 취약 시나리오에 필요한 syzlang, pseudo-syscall, arm 규칙을 만들 때 읽는
입력이기도 하다. 목표는 Agent가 **현재 퍼징 환경이 지원하는 범위 안에서** 산출물을 만들게 하는 것이다.
따라서 요소를 다루는 문서는 아래를 추가로 답한다.

| 항목 | 작성 내용 |
|---|---|
| 지원 범위 | 이 요소로 할 수 있는 것을 열거한다. 이름, 인자, 값 범위를 코드와 같은 철자로 쓴다 |
| 비지원 범위 | 할 수 없는 것, 시도하면 어떻게 실패하는가(오류 코드, 거부 카운터)를 쓴다 |
| 확장 절차 | 새 pseudo-syscall, 새 기술, 새 arm 규칙을 추가할 때 고칠 파일과 순서, 함께 갱신할 항목(`.const`, `alwaysSupported` 등)을 쓴다 |
| 제약 | 지원 범위 안에서도 지켜야 할 불변 조건(호출 순서, 자원 수명, lane 종속성)을 쓴다 |
| 검증 방법 | 만든 산출물이 환경에서 동작하는지 확인하는 방법을 쓴다(파서 통과와 실행 성공은 다르다) |

작성 시 주의:
- 지원 여부가 불확실하면 지원한다고 쓰지 않는다. `미검증`이라고 쓰고 확인 방법을 적는다.
- "사람은 알 만한" 암묵 지식을 남기지 않는다. 문서에 없으면 Agent는 없다고 가정한다.
- 확장 절차는 문서에 실제로 존재하는 파일과 심볼만 가리킨다. 존재하지 않는 절차를 상상해서 쓰지 않는다.
- 지원 범위가 코드 변경으로 달라지면 이 절을 함께 갱신한다. 낡은 지원 범위는 Agent를 오도한다.

## 9. 제출 전 점검표

- [ ] 요약이 세 문장 이내이고, 깨졌을 때 무엇이 잘못 보이는지 포함한다.
- [ ] `해결하려는 문제`가 관측된 증상으로 시작한다.
- [ ] 각 설계 결정에 근거가 대응한다.
- [ ] 버린 대안과 재검토 조건이 있다.
- [ ] 상류·하류·운영 영향을 모두 썼다.
- [ ] 신뢰성 요구가 오류 방향(거짓 양성/음성)을 명시한다.
- [ ] 검증 오라클이 *증명하지 않는 것*을 적었다.
- [ ] ASCII 다이어그램이 있고 경계·화살표 이름·범례를 갖췄다.
- [ ] 수치마다 출처가 있다.
- [ ] 미결·미검증을 결정된 것처럼 쓰지 않았다.
- [ ] 코드에서 확인한 심볼·경로가 실제로 존재한다.
- [ ] Agent가 쓸 요소는 지원 범위, 비지원 범위, 확장 절차, 제약, 검증 방법을 갖췄다.
